# 2026-08-22 — S11-1: 성능 재실측 (S3 기준선 갱신)

## 목표·범위

S3 성능 게이트(63페이지, 키 입력당 <30ms) 이후 S4~S10에서 얹은 기능
(IME, 6스토리 편집, Enter/병합, 노트 삽입·삭제, 빈 문단 세그먼트, 미주
타입 필드, 선택 편집)이 성능을 움직였는지 실측. bench.rs에 구조 연산
구간을 추가하고 브라우저 측정을 재실행. 최적화는 범위 밖(발견만 기록).

## 측정 환경

- 동일 700문단+표 14개 문서 (63페이지, out/bench.docx), 포크 7c114e8.
- 네이티브: `cargo run --release --bin bench` (+`RDOCX_BENCH_HF=1` 변형).
- 브라우저: 헤드리스, `state().lastMs`(wasm 호출 시간 = 증분 레이아웃 +
  델타 SVG + hits 직렬화), 2회 실행. 머신 노이즈 이력 있음 → min 중시.

## 결과 — 타이핑 (S3 대비 회귀 없음)

| 측정 | S3 기준선 | 현재 |
|---|---|---|
| 네이티브 키 입력 (HF off) | 24~30ms | mean 26 / min 23ms |
| 네이티브 키 입력 (HF+PAGE) | ~동일 | mean 24 / min 22ms |
| 브라우저 키 입력 | 64~103ms (부하 시 ~160) | min 69~71 / mean 100~121ms |

S4~S10 기능이 타이핑 핫패스와 직교함을 확인 — 증분 캐시(지문, 문단
캐시, 재시작 페이지네이션)는 그대로 작동.

## 결과 — 구조 연산 (신규 기준선)

노드 테이블이 바뀌어 페이지네이션 풀패스 폴백을 타는 연산들. 위치 3곳
(200/400/600문단)에서 각 1회, ms:

| 연산 | 네이티브 HF off | HF+PAGE | 브라우저 |
|---|---|---|---|
| Enter (분할) | 35~39 | 45~48 | ~500 |
| Backspace 병합 | 33~35 | 44~46 | ~450 |
| 형제 2문단 선택 삭제 | 32~35 | 47~53 | — |
| 각주 삽입 | 36~38 | 45~70 | — |
| 각주 삭제 | 35~36 | 42~49 | — |
| undo (스냅샷 복원) | — | — | ~400 |

- 네이티브 풀패스 폴백은 타이핑 대비 +10~20ms — 인터랙티브 예산 안.
- 브라우저 구조 연산 ~0.5s의 내역: 풀패스 wasm 레이아웃(~150ms 추정)에
  더해 **"33/62 pages redrawn"** — 문단 삽입/삭제가 F-X037 소스 노드
  id를 뒤로 연쇄 시프트시켜, 분할 지점 이후 모든 페이지의 SVG(data-hit
  경로)가 달라지고 DOM 교체 + 전 페이지 hits JSON 재직렬화가 따라옴.

## 발견 (최적화 백로그 후보, 이번 범위 밖)

1. **소스 id 연쇄 시프트**: 구조 연산 후 뒤쪽 모든 페이지가 "내용은
   같은데 주석(id)만 달라져" 다시 그려진다. 델타 해시를 id 제외 내용만
   으로 계산 + hits만 갱신하면 브라우저 구조 연산이 타이핑급으로 떨어질
   여지.
2. **hits JSON 전량 재직렬화**: 1페이지 변경에도 37k 히트 전체를 매번
   직렬화 — 변경 페이지만 보내도록 분리 가능.
3. cold layout 편차(1641 vs 578ms)는 디스크 캐시 워밍 차이로 판단.

## 결론

타이핑 핫패스는 기준선 유지(게이트 <30ms 계속 충족). 구조 연산은
네이티브에서 충분히 빠르나 브라우저에서 렌더·직렬화가 지배 — 다음
성능 단계가 필요하면 위 1·2번이 출발점.
