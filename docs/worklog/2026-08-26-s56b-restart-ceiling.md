# 2026-08-26 — S56b: 4줄 문단 1.3× 추적 → 32페이지 상한 발견, 회귀는 철회

## 목표·범위

S56에서 설명하지 못한 "4줄 문단 문서에서 v0.10.1이 1.3× 느리다"의 원인
특정. 포크 `exp/restart-gate`에 진단만 추가(프로덕션 무변경).

## 진단 도구 (포크 exp/restart-gate, 업스트림 제출용 아님)

- `RDOCX_RESTART_DEBUG=1` — 매 레이아웃마다 재시작 적격 플래그
  (`record_eligible`/`eligible`/`reusable_record`/`reusable`/`retained_ctx`
  + 섹션·각주·미주·머리글·wrap 여부)와 캐시 후보 크기·게시 여부 출력.
- `RDOCX_RESTART_LINE_CAP=N` — `paragraph.lines.len() <= 2` 상수 오버라이드.
- `RDOCX_SKIP_SPACING_RESHAPE=1` — v0.9.0+가 `build_breakable_segments`에
  추가한 세그먼트 전체 재shaping 생략.
- rdoc `bench2`에 `RDOC_BENCH2_PARAS=N`(문단 개수) 추가 — 문단 길이를
  고정한 채 **페이지 수만** 바꾸기 위함.

## 발견 ① — 재시작 캐시에 32페이지 상한이 있다

플래그 출력으로 4줄 문단 문서는 `record_eligible=false`, 1줄 문단 문서는
`true`임을 확인. 캡을 64로 올리면 `eligible=true`가 되지만
**`reusable_record=false`** — 적격이어도 캐시가 재사용되지 않는다.
게시 지점을 보면:

```rust
if restart_record_eligible
    && pages.len().max(checkpoints.len()) <= RESTART_CACHE_MAX_ENTRIES  // = 32
```

문단 길이를 1줄로 고정하고 **개수만** 늘려 페이지 수를 스캔한 결과
(v0.10.1, 키 입력 min ms):

| 문단 수 | 페이지 | min | 캐시 게시 |
|---|---|---|---|
| 400 | 13 | 1 | true |
| 700 | 22 | 3 | true |
| 1000 | 31 | 4 | **true** (bytes 5.43 MB / 8 MiB) |
| 1030 | 32 | 5 | true |
| 1060 | 33 | 6 | **false** |
| 1090 | 34 | 7 | **false** (게시 블록 미도달) |
| 2100 | 64 | 16 | false |

**33페이지부터 재시작 캐시가 아예 게시되지 않는다.** 우리 실문서는
브라우저 57페이지, 네이티브 벤치 63페이지 — 전부 상한 밖이다.
0.8은 같은 스캔에서 절벽 없이 매끄럽게 스케일한다(3→6→9→9→12→25 ms).

## 발견 ② — 4줄 문단 1.3× 회귀는 **철회**

같은 61페이지 문서로 A/B/A 교차 측정(각 5회, mean ms):

| | 측정값 | 중앙값 |
|---|---|---|
| A: v0.10.1 | 26 / 37 / 28 / 29 / 28 | 28 |
| B: 0.8 | 46 / 37 / 47 / 38 / 33 | 38 |
| A2: v0.10.1 (동일 빌드) | 42 / 37 / 38 / 37 / 37 | 37 |

**같은 빌드인 A와 A2가 28 vs 37로 갈린다.** 이 머신의 실행 간 편차가
±30%이고, A2와 B는 구분되지 않는다. S56에서 기록한 42~52 vs 31~41은
무거운 cargo/wasm 빌드 직후에 잰 값이라 부풀려진 것으로 보인다
(A2도 2m38s 빌드 직후였다).

→ **네이티브 `doc.layout()`에서 4줄 문단 회귀는 실재하지 않는다.**
S56 worklog·CLAUDE.md의 해당 서술을 철회한다.

## 발견 ③ — 추가 shaping은 원인이 아니다

v0.10.1이 `build_breakable_segments`에서 세그먼트 전체를 한 번 더
`shape_text`하는 것은 사실이나(0.8에 없음), 스위치로 껐을 때 차이가
없다(27/35/30 → 26/30/27). shaping memo가 흡수한다.

## 발견 ④ — 각주 절벽은 재확인됨 (#53 헤드라인 유효)

편차를 감안해 동일 빌드에서 교대 측정(4쌍):

| 쌍 | 각주 없음 | 각주 1개 |
|---|---|---|
| 1 | 2 ms | 14 ms |
| 2 | 3 ms | 17 ms |
| 3 | 4 ms | 12 ms |
| 4 | 2 ms | 11 ms |

겹침 없이 4~6×. #53에 올린 내용은 그대로 유효하다.

## 남은 문제 — 브라우저 회귀의 원인이 다시 열렸다

네이티브에서 회귀가 없는데 브라우저 프로덕션 A/B는 타이핑 1.46×,
undo 2.15×였다(워밍 후 3회씩, 편차보다 큼). 즉 그 회귀는 재시작 경로가
아니라 **브라우저만 타는 경로** — caller 폰트 + 별칭 40개 +
bundled-fallback(`layout_with_fonts_aliases_and_bundled_fallback`) 또는
SVG 델타 렌더 — 에서 온다고 봐야 한다. F-X051이 별칭 해석을 바꿨으므로
그쪽이 유력한 후보다. **미조사.**
