# 2026-08-21 — 타당성 검토와 PoC 1~3

## 조사

- rhwp(3.7k★, 450K LOC) 분석: 폐쇄 포맷 공백을 채운 성공. DOCX는 조건이
  다름 — 스펙 공개, 경쟁 존재(OnlyOffice/Collabora/ZetaOffice), Rust
  선행 크레이트 존재.
- rdocx 코드 분석 (클론, 27 크레이트 / Rust 162K LOC / 테스트 1,564개):
  oxml-*(포맷 중립 인프라) / rdocx-*(Word) / rpptx-*(PPT) 3계층.
  레이아웃 엔진은 harfrust 셰이핑 + 각주 선레이아웃 + anchored drawing까지
  갖춤. 반면 wasm 바인딩은 343줄(생성/변환만), 에디터·브라우저 렌더러 없음.
- 결론: 하단 절반은 rdocx 재사용, 에디터 계층에 집중 (decisions.md D1).

## PoC 1 — SVG 렌더러 (네이티브)

- 업스트림 클론에 `Document::layout()` 22줄 패치 (LayoutResult 공개).
- `GlyphRun`→`<use>`(글리프 벡터 defs), `Line`/`FilledRect`/`Path`/`Group`
  1:1 매핑. 데모 docx(스타일 혼합·한국어·리스트·표) 렌더.
- **검증**: 헤드리스 브라우저 스크린샷 vs rdocx 자체 PNG 백엔드 — 시각적
  일치. 143 글리프 defs / 559 use, 140KB (gzip 40KB).
- 발견 1: scale 소수 2자리 반올림 → 글리프 28% 오차 (7자리로 해결).
- 발견 2: **글자 중복 렌더링("ttf-pparser")이 SVG·PNG 양쪽 동일** → 원본
  docx 텍스트는 정상 → 업스트림 레이아웃 버그로 판정.

## PoC 2 — wasm

- lib/bin/wasm 3분할, `wasm-pack build --target web --no-default-features`.
- 폰트 주입 API(`add_font`) — 브라우저가 fetch한 Malgun Gothic으로 한국어
  셰이핑 확인.
- **검증** (헤드리스 자동화): 데모 92.6ms, .docx 파일 파싱 포함 36.6ms.
  wasm 10.4MB / gzip 4.8MB.

## PoC 3 — 히트테스팅/편집 루프

- 렌더러가 히트맵 출력: `data-hit` ID + 좌표/문자 advance/원문/문서 위치.
- 문서 위치는 순차 텍스트 매칭으로 역산 — 156/174 매핑, 미매핑 18 = 불릿
  마커 + 표 셀 (provenance 공백의 정량 근거).
- 편집: `insert_at`/`delete_char_before` (런 경계 보존) + wasm
  `SvgConverter.insert/delete` 재조판.
- **검증** (헤드리스 자동화, `window.__t` 훅):
  - 제목 클릭 → para 0 off 8, "XYZ" 삽입 → "rdocx SVXYZG…" 정확, 백스페이스
    3회 원복. **키 입력당 21~27ms** (전체 재조판+재렌더+DOM 교체).
  - 한국어 문단 클릭 → "한글 입력 테스트! " 삽입 → 줄바꿈 재계산 확인 (22ms).
  - 표 셀 클릭 → "no document mapping" 안내 후 편집 차단.
  - 증거: docs/evidence/editor-korean-insert.png 외.
