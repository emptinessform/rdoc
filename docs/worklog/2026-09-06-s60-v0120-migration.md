# 2026-09-06 — S60: v0.12.0 이행 (MultilingualText 지원 + 회귀 원인 확정)

S59에서 v0.12.0의 성능은 확인됐지만 두 가지가 남았다: `MultilingualText`
미지원(기능 결손)과 구조 편집 회귀. 사용자 결정은 **"MultilingualText 지원
후 이행, Enter/각주 회귀는 이슈로 올리고 안고 간다"**.

## 1. MultilingualText 렌더·히트 지원

### 무엇이 문제였나

v0.12.0 `engine.rs:5448`은 문단이 다음 중 하나면 문단 전체를 다국어 셰이핑
경로로 보내고 `PositionedElement::MultilingualText`를 내보낸다:

- 문단 base direction이 `Auto`가 아니거나,
- 런 중 하나라도 direction이 `Auto`가 아니거나,
- 텍스트에 CJK 표의문자(U+3400–9FFF, **한자 포함**), 가나(U+3000–30FF),
  태국어, 데바나가리, 히브리/아랍이 있으면.

**한글(U+AC00–D7AF)은 트리거가 아니다.** 그래서 데모 문서·bench.docx는
멀쩡했고 브라우저 배터리도 통과했지만, LibreOffice가 방향 속성을 붙여
내보내므로 CJK가 전혀 없는 문서도 이 경로를 탄다. rdoc은 `GlyphRun`만
알아서 코퍼스 14개 중 7개가 백지였다.

### 어떻게 고쳤나

`MultilingualGlyphRun::legacy_projection()`이 `GlyphRun`과 글리프 단위로
동일한 값을 준다(원점·폰트·글리프 id·x 어드밴스·논리 텍스트·소스 스팬).
따라서:

- **히트**: `push_hit(&run.legacy_projection())` — 논리 텍스트, 문자별
  어드밴스, 소스 스팬 의미가 그대로 유지된다. 새 코드 없음.
- **렌더**: `emit_glyph_run`을 공용 페인터
  `emit_positioned_glyph_run(out, run, x_offsets, y_offsets, y_advances)`로
  쪼갰다. 평범한 `GlyphRun`은 세 배열이 비어 있다. 부호는 rdocx 자체
  래스터라이저를 따랐다 — 글리프는 `(pen_x + x_offset, pen_y - y_offset)`에
  놓고 펜은 `(+x_advance, -y_advance)`만큼 움직인다.
- **해시**: `hash_elements`에 대응 arm을 추가해 다국어 스팬이 바뀌면 그
  페이지가 무효화되게 했다.
- `is_valid()`가 false인 런은 경고 카운트만 올리고 건너뛴다.

### 검증

코퍼스가 14/14로 복귀했고 **문서별 SVG 바이트 크기가 v0.8 핀과 전부
동일**하다. 더 강한 확인으로 SVG에서 글리프 배치 좌표를 뽑아 비교했다:

| 문서 | v0.8 글리프 | v0.12 글리프 | 좌표 |
|---|---|---|---|
| comment | 28 | 28 | **완전 일치** |
| header_footer | 22 | 22 | **완전 일치** |
| font (일본어 こんにちは 世界) | 14 | 14 | **완전 일치** |

run 수는 3개 문서에서 늘었다(comment 7→12, header_footer 5→7, image 1→2).
다국어 셰이핑이 스크립트·bidi 경계에서 스팬을 쪼개기 때문이며, 전부
문단에 매핑된다(mapped == runs).

네이티브 PoC는 2페이지 / 167+12 KB / 히트 272(264 매핑)로 v0.8과 동일.
브라우저 배터리 **50 PASS / 0 FAIL**.

## 3. 남은 회귀의 원인 확정

S59는 "재시작 레코드 재발행 비용으로 보인다"까지였다. S60에서 계측으로
확정했다.

### 문서 크기에 따른 기울기 (min ms, `RDOC_BENCH_PARAS`)

| 문단 수 | 페이지 | 타이핑 v0.8 → v0.12 | 각주 삽입 v0.8 → v0.12 |
|---|---|---|---|
| 100 | 9 | 6 → **3** | 8 → 20 (2.5×) |
| 200 | 18 | 8 → **5** | 13 → 38 (2.9×) |
| 400 | 36 | 18 → **7** | 22 → 86 (3.9×) |
| 700 | 63 | 34 → **13** | 57 → 158 (2.8×) |

추가 확인 2라운드(200/400문단, 삽입·삭제 모두): 12/12 → 39/37,
25/27 → 89/90, 14/14 → 38/39, 24/23 → 79/79. **전부 패, 예외 없음.**
비용이 문단 수에 비례한다 = **블록당 비용**이다.

### 계측 (`exp/s60-identity`, `RDOCX_DIAG_IDENTITY=1`)

`restart_body_identity` 호출 수를 레이아웃마다 셌다. 715블록 문서:

```
타이핑 10회:  reusable=true  prefix=357 suffix=357 blocks=715 identity_calls=1072
Enter ×3:     reusable=false prefix=0   suffix=0   blocks=716/717/718 identity_calls=716/717/718
병합·선택삭제: reusable=false prefix=0   suffix=0   identity_calls=N
각주 삽입·삭제: reusable=false prefix=0   suffix=0   blocks=712 identity_calls=712
```

원인은 `engine.rs`의 `reusable_restart_record`가 요구하는 두 조건이다:

```rust
cache.body.iter().flat_map(|e| e.note_references()).eq(body_note_references(input))
&& (sources.is_none() || cache.body.len() == input.document.body.content.len())
```

- **각주 추가/삭제**는 첫 조건(문서 전체 노트 참조 시퀀스 동일성)을 깬다.
- **Enter/병합/선택 삭제**는 본문 블록 수를 바꾸므로, provenance가 켜진
  경우(=rdoc의 모든 경로) 둘째 조건을 깬다.

둘 중 하나라도 깨지면 `first_changed`/`common_suffix`가 `None`이 되고
레코드 재구축이 `prefix=0, suffix=0`으로 떨어져 **본문 블록마다**
`restart_body_identity`(= `CT_Document::to_xml`)를 부른다. 바뀐 블록은
하나인데 전 문서를 직렬화하는 셈이다.

부수 관찰: **빠른 경로(타이핑)조차** prefix/suffix 스캔이 일치하는 블록마다
identity를 직렬화해 레이아웃당 ~1.5N회를 쓴다(715블록에 1072회). v0.8보다
여전히 2.4배 빠르지만, 여기도 지문 비교만으로 끊을 여지가 있어 보인다.
