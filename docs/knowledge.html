브라우저에서 도는 DOCX(워드 문서) 편집기를 만들면서 배운 것들을, 처음 보는 사람도 따라올 수 있게 정리한 노트입니다. 작업이 진행될 때마다 절이 추가됩니다.

1. 이 프로젝트는 무엇을 하나

.docx 파일을 읽어서 브라우저 화면에 실제 종이처럼 그려 주고, 그 위에서 바로 타이핑해 고칠 수 있는 가벼운 편집기를 만들고 있습니다. 무거운 계산(글자 배치, 페이지 나누기)은 wasm으로 컴파일된 Rust 코드가 하고, 화면 그리기는 SVG(벡터 그림)로 합니다. 레이아웃 엔진은 오픈소스 rdocx를 가져다 쓰고, 필요한 개선은 업스트림(원 저장소)에 제안해 되돌려주고 있습니다.

2. 키 하나 누르면 무슨 일이 벌어지나 — 레이아웃 파이프라인

워드 프로세서는 글자 하나를 끼워 넣을 때마다 "이 문단은 몇 줄이 되지? 줄이 늘면 다음 페이지로 밀리나?"를 다시 계산해야 합니다. 이 계산 전체를 재조판(relayout)이라고 부릅니다. 단계는 이렇습니다.

블록(block)
문단 하나를 페이지 폭에 맞춰 줄바꿈까지 끝낸 결과물. "이 문단은 이 3줄이다"라는 완성된 조각입니다. 표도 하나의 블록이 됩니다.
셰이핑(shaping)
"안녕 hello"라는 글자열을 글꼴 파일에 물어봐서 실제 글자 모양(글리프)과 각 글자의 폭으로 바꾸는 일. 한글·아랍어처럼 글자가 이어 붙는 문자 때문에 생각보다 비싼 계산입니다.
페이지네이션(pagination)
완성된 블록들을 위에서부터 페이지에 채워 넣다가, 넘치면 다음 페이지로 넘기는 일. "몇 쪽짜리 문서인가"가 여기서 정해집니다.

3. 왜 느렸고, 캐시가 어떻게 살렸나

처음 측정했을 때 63페이지 문서에서 키 하나에 1,144ms가 걸렸습니다. 1초가 넘으니 타이핑이 불가능한 수준입니다. 범인을 찾아 보니 대부분이 "매번 똑같은 일을 처음부터 다시 하는" 비용이었습니다.

범인무슨 일비용
시스템 글꼴 스캔PC에 설치된 글꼴 전부를 매번 다시 읽음~750ms
글꼴 파일 복사13~20MB짜리 한글 글꼴 파일을 매번 다시 읽고 복사~230ms
블록 다시 만들기안 바뀐 700개 문단도 전부 다시 줄바꿈~100ms
페이지네이션63페이지 전부 다시 배분~19ms

해법은 전부 같은 아이디어입니다 — 한 번 한 일의 결과를 저장해 두고(캐시), 다음에 같은 일이 오면 저장본을 꺼내 쓴다. 글꼴 스캔은 프로세스당 1회로, 글꼴 파일은 경로별로 1회만 읽게, 셰이핑 결과는 (글꼴, 글자열, 크기)를 키로 저장, 블록은 "문단 내용이 안 바뀌었으면 지난번 블록 재사용"으로. 이 네 개의 캐시로 1,144ms → 101ms, 이후 개선(4·5절)으로 37ms까지 왔습니다.

핵심 교훈 — 편집기는 변환기와 다릅니다. 파일을 한 번 변환할 때는 안 보이던 비용이, 키 입력마다 반복되면 전부 "키 하나당 비용"이 됩니다. 그래서 편집기의 성능 작업은 대부분 "반복되는 같은 일 찾아서 캐시하기"입니다.

4. 지문(fingerprint) — "그대로네요"를 빨리 알아내는 법

"이 문단, 지난번과 같은가?"를 판단하려고 문단 전체를 글자 하나하나 비교하면 그것도 느립니다. 대신 문단 내용을 하나의 큰 숫자로 요약합니다. 이 요약값을 해시(hash) 또는 지문이라고 부릅니다. 내용이 같으면 지문이 같고, 내용이 다르면 (사실상 확실하게) 지문이 다릅니다. 숫자 하나 비교로 "같다/다르다"가 끝납니다.

처음엔 문단 구조를 통째로 디버그 문자열로 찍어서(format!("{:?}")) 그걸 해시했는데, 이 "문자열 만들기" 자체가 키 입력당 ~20ms를 먹었습니다. 그래서 전용 워커를 만들었습니다: 본문 글자는 바이트 그대로 해시하고, 서식 정보 같은 작은 구조만 디버그 문자열을 거치게. 요약 대상은 같지만 요약을 만드는 비용이 확 줄었습니다.

캐시의 함정 — 캐시 키(지문)에 빠진 정보가 있으면, 실제로는 바뀌었는데 "같다"고 판단해 낡은 결과를 내놓습니다(stale). 예: 번호 매기기 목록의 "3."이라는 번호는 문단 자신이 아니라 앞 문단들이 몇 개였는지에 달려 있어서, 문단 내용만 지문 찍으면 놓칩니다. 그래서 번호 달린 문단은 블록 캐시에서 제외했습니다. 캐시 설계의 반은 "키에 뭘 넣을지" 고민입니다.

5. undo를 눌러도 캐시가 살아남게 — 엔진 이월

undo(되돌리기)는 "예전 문서 상태를 통째로 복원"하는 방식이라, 문서 객체를 새로 만듭니다. 그런데 캐시(셰이핑 메모, 블록 캐시)는 낡은 문서 객체 안의 엔진에 붙어 있어서, 새 객체를 만들면 캐시가 통째로 버려졌습니다. 그래서 undo 직후 첫 재조판이 타이핑의 2배쯤 느렸습니다.

해결은 이사할 때 가구를 들고 가는 것과 같습니다: 문서 객체를 갈아끼우기 전에 낡은 객체에서 엔진(캐시 포함)을 꺼내서 새 객체에 넣어 주는 두 개의 API를 만들었습니다 (take_layout_engine / set_layout_engine). 캐시는 내용 기준(지문 키)이라 어느 문서 객체에 붙어 있든 안전합니다. 결과: undo/redo가 타이핑과 같은 속도(75~91ms→wasm 기준)가 됐습니다.

6. 재시작 가능한 페이지네이션 (완료 — 키 입력당 37→24~30ms)

지금 키 입력당 남은 비용의 큰 덩어리 하나가 페이지네이션(12~15ms)입니다. 글자 하나 고쳤는데 63페이지 전부를 다시 배분하고 있기 때문입니다. 그런데 생각해 보면: 5페이지의 문단 하나를 고치면 1~4페이지는 절대 안 바뀌고, 줄 수가 그대로면 6페이지 이후도 안 바뀝니다.

세 가지 재료로 만듭니다.

  1. 블록 지문 목록 — 이번 키 입력의 블록 지문들과 지난번 지문들을 나란히 비교하면 "몇 번째 블록부터 달라졌나"(분기점)가 나옵니다.
  2. 체크포인트 — 페이지네이션 도중 "이 블록이 새 페이지를 깨끗하게 시작했다"는 지점을 기록해 둡니다. 깨끗하다 = 문단이 페이지에 걸쳐 쪼개지지 않았고, 이월된 각주도 없음. 여기서는 페이지네이터의 기억(상태)이 사실상 비어 있어서, 나중에 그 지점부터 재시작해도 결과가 같습니다.
  3. 재접합(splice) — 분기점 이후를 다시 배분하다가 "남은 블록들이 지난번과 완전히 같고, 지금 쪽수도 지난번과 같다"는 지점에 도달하면, 지난번 뒤쪽 페이지들을 통째로 이어 붙이고 멈춥니다. 타이핑은 대부분 페이지 수를 안 바꾸므로 실질적으로 1~2페이지만 다시 배분하게 됩니다.
왜 조심해야 하나 — 페이지는 앞뒤 문맥의 영향을 받습니다. 예를 들어 "다음 문단과 떨어지지 말 것(keep-with-next)" 속성은 다음 블록의 첫 줄 높이를 미리 보고, 떠 있는 그림(floating drawing)은 뒤쪽 블록이 앞쪽 페이지에 그림을 얹을 수도 있습니다. 각주는 페이지를 넘어 이어질 수 있습니다. 그래서 이런 영향이 있는 문서(떠 있는 그림, 다중 섹션 등)는 안전하게 전체 페이지네이션으로 폴백하고, 체크포인트도 영향 범위 밖에서만 잡습니다. 그리고 항상 "캐시 경로 결과 == 전체 재계산 결과"를 테스트로 강제합니다.

결과: 페이지네이션 12~15ms → 1~3ms. 63페이지 중 실제로 다시 배분하는 건 바뀐 곳 주변 4페이지뿐입니다("29 prefix + 4 rebuilt + 30 spliced"). 표(테이블)도 문단처럼 지문 키로 캐시해서, 키 입력당 전체가 평균 24~30ms — 목표였던 30ms 게이트에 도달했습니다.

7. 완성하며 배운 것 — 체크포인트의 함정과 공유의 힘

함정 1: 체크포인트를 어디서 잡을 것인가

처음엔 "블록 목록을 도는 루프의 맨 위에서, 페이지가 깨끗하면 체크포인트"라고 구현했습니다. 돌려 보니 체크포인트가 단 하나도 안 잡혔습니다. 이유: 페이지 경계는 루프 사이에서 생기지 않습니다. "이 문단이 남은 공간에 안 들어가네 → 페이지 마감 → 새 페이지에 문단 배치"가 문단 배치 함수 안에서 일어나기 때문에, 루프 맨 위로 돌아왔을 때는 이미 새 페이지에 내용이 놓인 뒤입니다. 체크포인트는 블록 배치 함수의 입구에서 잡아야 했습니다. 교훈: 상태를 기록할 때는 "언제 이 상태가 실제로 존재하는가"를 코드 흐름에서 확인할 것. 머리로 그린 루프와 실제 제어 흐름은 다릅니다.

함정 2: 아껴 놓고 복사로 다 쓰기

재사용이 작동한 뒤에도 전체 시간이 오히려 늘었습니다. 범인은 복사: 캐시가 페이지를 보관하려면 호출자에게 내줄 사본이 필요한데, 63페이지를 통째로 깊은 복사하는 데 ~12ms — 아낀 페이지네이션 비용과 맞먹었습니다.

해법은 Rust의 Arc(참조 카운트 공유 포인터): 페이지를 복사하는 대신 "같은 원본을 가리키는 손잡이"만 나눠 갖습니다. 복사가 0ms가 되는 대신, 누군가 페이지를 고쳐야 할 때(쪽번호 필드 치환 등)만 그 페이지 하나를 그때 복사합니다(copy-on-write). 교훈: 캐시의 이득은 데이터를 꺼내는 비용까지 계산해야 진짜 이득입니다. 그리고 성능 작업은 반드시 단계마다 실측 — "빨라졌겠지"는 두 번 틀렸습니다.

8. 한글 입력의 비밀 — IME 조합과 undo 묶기

영어는 키 하나 = 글자 하나지만, 한글은 ㅎ + ㅏ + ㄴ = 한처럼 여러 키가 모여 한 글자가 됩니다. 이 조립을 해 주는 OS 프로그램이 IME입니다. 브라우저는 조립 과정을 세 가지 이벤트로 알려줍니다: compositionstart(조립 시작) → compositionupdate (조립 중 — "ㅎ", "하", "한"으로 계속 바뀜) → compositionend(확정).

에디터는 update가 올 때마다 "직전 조합 글자를 지우고 새 것을 넣기" (replace_range)로 화면에 실시간 반영합니다. 글자 하나 바뀔 때마다 전체 재조판이 돌지만, 3~7절의 성능 작업 덕분에 키당 수십 ms — 실시간으로 충분합니다. 성능 작업이 기능을 가능하게 만든 순서인 셈입니다.

핵심 문제는 undo의 단위였습니다. 에디터는 편집 전마다 문서 스냅샷을 undo 더미에 쌓는데, 조합 중간 단계도 편집이라 "한" 하나에 스냅샷이 3장 쌓였습니다. 해법: 조합 시작에 스냅샷 1장만 쌓고, 조합 중에는 쌓지 않는 플래그(begin_composition/end_composition)를 두었습니다. 조합을 취소하면(빈 문자열로 끝나면) 문서가 스냅샷과 똑같아지므로 그 스냅샷도 지워서, undo를 눌렀을 때 "아무 일도 안 일어나는 한 번"이 생기지 않게 했습니다.

배운 것 — 사용자 눈에 보이는 것(화면 갱신)과 역사에 남는 것(undo 단위)은 별개의 축입니다. "보이는 건 잘게, 기록은 굵게"가 편집기의 기본 문법: 조합뿐 아니라 나중에 드래그, 자동 교정, 붙여넣기 정리에도 같은 원리가 쓰입니다. 검증도 이 축대로: 중간 상태는 이벤트 사이에 화면 텍스트를 검사하고, undo는 횟수를 세어 검사했습니다 (시나리오 7개 자동화, 전부 통과).

덧붙임: 프리에딧 밑줄은 문서가 아니라 유리판에

조합 중인 글자 아래 밑줄(미확정 표시)을 그릴 때, 문서에 밑줄 서식을 넣었다 뺐다 하면 undo 정합이 다시 복잡해집니다. 대신 캐럿·선택 하이라이트와 같은 방법을 썼습니다: 문서 위에 겹쳐진 투명한 "유리판"(SVG 오버레이)에만 밑줄을 그리는 것. 문서는 밑줄의 존재를 모르므로 확정하든 취소하든 지울 게 없습니다. UI에서 "일시적 표시는 오버레이, 영구적 내용은 문서"로 층을 나누면 상태 관리가 극적으로 단순해집니다.

9. 지문에 숨어든 일련번호 — 조용히 죽는 캐시

쪽번호 꼬리글("Page N")을 벤치마크에 넣자 캐시가 전부 빗나가기 시작했습니다. 진단 로그는 매 키 입력마다 "환경이 바뀌었다"고 했지만, 문서는 아무것도 안 바뀌었습니다. 구성 요소별로 해시를 쪼개 찍어 보니 꼬리글 해시만 매번 달랐습니다.

범인: 필드 구조체가 디버깅용으로 갖고 있는 source_id — 파싱할 때마다 전역 카운터에서 새 번호를 받습니다. 우리 지문은 구조체의 디버그 출력을 통째로 해시했으므로, 내용과 무관한 일련번호가 매번 지문을 바꿔 놓았습니다. 조용한 실패라 더 위험합니다: 결과는 여전히 정확하고, 그저 느릴 뿐이니까요. 수정: 필드는 디버그 출력 대신 레이아웃이 실제로 읽는 것만(명령 문자열, 저장된 표시값, dirty 플래그) 해시.

배운 것 두 가지. ① 캐시 키에 "편하게" 디버그 문자열을 쓰면, 그 안에 뭐가 들었는지 모른 채 서명하는 셈입니다. 키에는 의미 있는 필드만 명시적으로 넣을 것. ② 캐시는 조용히 죽습니다 — 정확성 테스트로는 안 잡힙니다. "캐시가 맞았는가"를 보여 주는 진단 로그(우리는 RDOCX_TIMING)를 처음부터 심어 두면, 이런 문제가 수치("env changed" 10회)로 바로 드러납니다.

10. 글자는 자기가 어디서 왔는지 안다 — 소스 맵과 표 셀 편집

화면의 글자를 클릭했을 때 "문서의 어느 문단, 몇 번째 글자"인지 알아내는 것을 역매핑이라 합니다. 지금까지는 레이아웃 결과에 출처 정보가 없어서, 화면 글자열을 문서 텍스트에서 검색해 위치를 추측했습니다 (텍스트 매칭). 같은 문구가 두 번 나오면 틀릴 수 있고, 표 셀은 아예 포기했었습니다.

업스트림에 제안했던 provenance(출처 추적)가 v0.8.0에 공식 탑재되면서, 이제 레이아웃 결과의 모든 글자 조각이 "나는 문서의 이 문단의 이 글자 범위다"라는 증명서를 달고 나옵니다. 우리는 그 증명서를 경로 문자열("d/8.1.0.0" = 본문 8번째 항목인 표의 1행 0열 첫 문단)로 바꿔 화면 글자마다 붙여 두고, 클릭하면 그 경로로 문서를 직접 수정합니다. 추측이 확신이 되자 표 셀 편집이 그냥 열렸습니다 — 타이핑, 한글 조합, 선택 대치, undo까지 본문과 동일하게.

배운 것 — 주소를 설계할 때 "지금 화면의 몇 번째"(결과-로컬 id)와 "문서 구조상 어디"(경로)를 구분해야 합니다. id는 레이아웃마다 바뀌지만 경로는 편집 전후로 안정적이라, JS 쪽 캐럿/선택 상태는 전부 경로로만 들고 있습니다. 그리고 인프라(소스 맵)를 업스트림에 제안해 공식화되면, 그 위의 기능(셀 편집)은 우회로를 걷어내는 것만으로 완성됩니다 — 우회는 빚이고, 인프라 기여가 상환입니다.

덧붙임: 머리글은 "다른 서랍"에 산다

같은 경로 체계로 머리글/꼬리글 편집도 열었습니다. 차이점 하나: 본문 문단은 메모리의 문서 트리에 그대로 살지만, 머리글은 .docx 안의 별도 XML 파트(다른 서랍)에 직렬화되어 있습니다. 그래서 편집이 "꺼내기 (파싱) → 고치기 → 다시 넣기(재직렬화)" 3단계가 되고, 서랍 안의 다른 것 (이미지 참조 등)은 건드리지 않도록 파트의 관계 목록은 보존합니다. 경로의 스토리 접두사(d/ h/ f/)가 곧 "어느 서랍인지"를 말해 주므로, 편집 연산 자체는 세 곳이 완전히 동일한 코드를 씁니다. 꼬리글의 쪽번호처럼 계산되는 글자는 출처 증명서가 없어서(의도된 설계) 클릭해도 캐럿이 서지 않습니다 — 편집 불가가 곧 안전장치입니다.

덧붙임 2: 각주는 타입 필드, 미주는 서랍 — 그리고 진실의 원천

각주/미주 편집으로 6개 스토리가 모두 열렸습니다. 재미있는 비대칭: 같은 라이브러리 안에서 각주는 메모리의 타입 구조(꺼내기 없이 바로 수정)로, 미주는 머리글처럼 서랍(XML 파트)으로 살고 있었습니다. 경로 디스패치 덕에 우리 편집 코드는 이 차이를 몰라도 됩니다.

그런데 여기서 기존 결함이 하나 드러났습니다: 레이아웃이 각주를 읽을 때 서랍(파트)만 봐서, 방금 메모리에 추가한 미저장 각주가 화면에 안 나왔습니다. 같은 데이터가 두 곳에 살면 반드시 어느 쪽이 진실의 원천(source of truth)인지 정하고 모든 읽기가 그쪽을 보게 해야 합니다 — 열 때 서랍→메모리로 올리고 편집은 메모리에 하는 구조라면, 읽기도 메모리를 봐야죠. 문서 변환기에서는 안 드러나던 이 불일치가 (항상 저장본을 읽으니까), 라이브 편집기를 얹자마자 드러났습니다. 새로운 소비자는 오래된 코드의 숨은 가정을 시험하는 가장 좋은 도구입니다.

덧붙임 3: 미주의 승격 — 비대칭을 없애는 리팩터링

덧붙임 2의 비대칭(각주=타입 필드, 미주=서랍)을 결국 없앴습니다. 미주도 각주와 똑같은 타입 필드가 됐습니다. "승격(promotion)"이라고 부르는 이유는, 데이터의 지위가 바뀌기 때문입니다: 편집할 때마다 서랍에서 꺼내 파싱하고 다시 직렬화해 넣던 XML 덩어리가, 열 때 한 번만 파싱되어 메모리에 상주하는 구조체가 됩니다. 

승격 전 (서랍 방식)                  승격 후 (타입 필드)
─────────────────────                ─────────────────────
편집 1회마다:                        열 때 1회:
  파트 XML 읽기                        파트 XML → 구조체
  → 파싱 → 수정                      편집 1회마다:
  → 직렬화 → 파트에 쓰기               구조체를 그 자리에서 수정
                                        (dirty 표시만)
저장할 때:                           저장할 때:
  이미 파트에 있음                     dirty면 구조체 → XML 한 번

승격이 가져오는 규칙 세 가지가 핵심입니다. ① 열 때 올리기: 파트가 있으면 파싱해 필드에 담는다. ② 읽기는 필드를 본다: 레이아웃도 저장 전의 편집을 바로 본다(덧붙임 2의 각주 결함이 미주에서는 처음부터 없음). ③ 저장은 dirty일 때만: 편집한 적 없으면 원본 파트 바이트를 그대로 보존한다 — 우리가 만들지 않은 문서를 함부로 다시 직렬화하지 않는 예의입니다.

승격의 보상은 즉시 나타났습니다: 미주의 Enter(분할)/Backspace(병합)가 각주와 같은 몇 줄짜리 함수로 끝났고, wasm 쪽에서 "미주는 미지원"이라고 거절하던 두 분기가 실제 구현 호출로 바뀌었습니다. 같은 모양의 데이터는 같은 모양의 코드로 다뤄야 특수 사례가 사라집니다.

후속으로 삽입/삭제(Ctrl+Alt+E, Ctrl+Alt+D)도 각주판을 거의 그대로 옮겨 끝났습니다 — 승격 이후 두 노트는 코드에서 구별할 이유가 참조 런의 태그 이름(footnoteReference vs endnoteReference) 하나뿐이기 때문입니다. 단축키 쪽에서는 반대 방향의 통합을 했습니다: 삭제는 Ctrl+Alt+D 하나로 두고 캐럿이 서 있는 경로의 접두사(fn/, en/)로 어느 노트인지 판별합니다. 사용자에게는 "지금 있는 곳을 지운다"라는 하나의 개념이지, 노트 종류별 단축키 두 개가 아니니까요.

11. 여러 문단을 지우는 일 — 형제, 흩어짐, 그리고 트랜잭션

드래그 선택이 문단 하나를 벗어나는 순간, "지우기"는 갑자기 어려운 문제가 됩니다. 선택이 어디서 시작해 어디서 끝나느냐에 따라 완전히 다른 두 가지 모양이 나오기 때문입니다. 

모양 1: 형제(siblings)                모양 2: 흩어짐(scatter)
같은 상자 안의 이웃 문단들            상자 자체가 다름 (셀 → 옆 셀)

  ┌─ 셀 ──────────┐                    ┌─ 셀A ──┐ ┌─ 셀B ──┐
  │ 문단1  Te[xt   │                    │ T[ext  │ │ Gl]yph │
  │ 문단2  ab]cd   │                    └────────┘ └────────┘
  └───────────────┘
  → Word처럼: 머리 꼬리 자르고,        → 셀 구조는 못 합침!
    중간 비우고, 하나로 병합             각 문단에서 텍스트만 걷어냄

모양 1은 어느 상자든 같은 알고리즘입니다: 첫 문단의 꼬리를 자르고, 마지막 문단의 머리를 자르고, 중간 문단들을 비운 뒤, 전부 첫 문단으로 병합. 본문·표 셀·머리글·각주·미주가 이미 "이전 형제로 병합"이라는 공통 연산을 갖고 있어서(10장, 덧붙임 3), 새 코드는 어느 상자인지 묻지 않는 40줄짜리 함수 하나로 끝났습니다. 경로에서 마지막 숫자만 떼면 "상자 열쇠"가 되고, 열쇠가 같으면 형제입니다.

모양 2는 Word도 구조를 합치지 않습니다 — 셀을 넘는 선택을 지우면 텍스트만 사라지고 표는 그대로죠. 우리도 같은 근사를 씁니다: 화면의 히트 목록(글리프가 어느 문단 몇 번째 글자인지)을 걸어가며 선택이 덮은 문단별 구간을 모아, "이 문단의 [1..4), 저 문단의 [0..2)를 지워라"라는 목록 하나를 wasm에 넘깁니다. 문단이 다르면 서로 오프셋을 흔들지 않으니 순서 걱정도 없습니다.

그리고 이번 단계의 진짜 교훈은 셋째 것입니다: 여러 단계짜리 연산은 실패도 여러 단계에서 할 수 있다. 표를 가로지르는 선택(중간에 표가 끼면 병합 불가)을 거부하는 테스트에서, 거부는 됐는데 첫 문단의 꼬리는 이미 잘려 있었습니다. 편집 코어가 "실패 시 체크포인트만 버리고 문서는 그대로" 두는 구조였는데, 단일 문단 연산에서는 실패=아무 일도 안 일어남이라 몇 달을 숨어 있던 결함입니다. 수정은 트랜잭션 규칙 그대로: 실패하면 체크포인트로 되돌린다. "부분 성공"은 편집기에서 데이터 손상과 같은 말입니다.

덧붙임: 화면은 한 장이지만 문서는 여러 겹 — 그리고 이벤트는 움직여야 온다

캐럿 ↑/↓ 구현에서 배운 것: 화면에서 "바로 아래 줄"을 찾으면 안 됩니다. 페이지 하단에는 본문 다음에 각주 블록과 꼬리글이 그려져 있지만, 그것들은 본문의 다음 줄이 아니라 다른 이야기(story)의 줄입니다. Word에서 본문 마지막 줄에서 ↓를 누르면 각주를 건너뛰어 다음 페이지 본문으로 가죠. 그래서 줄 이동은 "가장 가까운 줄"이 아니라 "같은 스토리의 가장 가까운 줄"을 찾습니다 — 경로 접두사(d/, fn/, en/…) 하나만 비교하면 끝나는 필터인데, 이게 화면 좌표에는 없는 문서의 논리 구조를 좌표 검색에 되살려 줍니다.

드래그 자동 스크롤에서 배운 것: 브라우저 이벤트는 변화가 있어야 옵니다. 마우스 버튼을 누른 채 화면 가장자리에 포인터를 가만히 대고 있으면 mousemove는 더 이상 오지 않습니다. 그래서 "가장자리에 있는 동안 계속 스크롤"은 이벤트 핸들러만으로는 못 만들고, 마지막 포인터 위치를 기억해 두고 requestAnimationFrame 루프가 매 프레임 스크롤 + 선택 재확장을 반복해야 합니다. 이벤트는 상태 변화의 통지이고, 지속 동작은 루프의 몫 — UI 코드의 오래된 이분법입니다.

덧붙임 2: 폭이 0인 글자 — 선택이 마커를 덮으면

각주 마커(²)는 화면에서는 글자 하나지만, 우리 텍스트 오프셋 공간에서는 폭이 0입니다(참조 런은 텍스트가 없으니까). 그래서 선택을 지울 때 마커가 그냥 살아남는 유령 문제가 있었습니다 — 텍스트만 다듬는 삭제에는 걸릴 것이 없으니까요. Word는 마커가 선택 안에 있으면 노트째 지웁니다.

해법은 삭제 전에 "이 범위가 어떤 마커를 덮나"를 따로 묻는 것입니다. 마커의 위치를 그 앞에 있는 텍스트 글자 수로 정의하면, 범위 [start, end)가 마커를 덮는 조건은 start < pos < end. 재미있는 구석 두 가지: ① 폭이 0이라 경계에 정확히 걸린 마커는 선택 안인지 밖인지 원리적으로 구별 불가입니다(캐럿이 마커 앞인지 뒤인지가 같은 오프셋). 보수적으로 "확실히 내부일 때만" 지웁니다. ② 노트 제거를 텍스트 삭제보다 먼저 해도 됩니다 — 참조 런은 폭이 0이라 문자 오프셋을 하나도 안 흔들거든요. 순서에서 자유로우면 코드가 단순해집니다.

마지막 퍼즐 조각은 표를 가로지르는 본문 선택이었습니다. 형제 알고리즘의 "중간 문단 비우기"는 중간이 표면 실패합니다(§11의 원자적 거부가 그 지점). 그런데 본문 최상위에서는 형제 인덱스가 곧 body content 인덱스라, 중간을 "비우기" 대신 통째로 제거하면 문단이든 표든 같은 코드로 사라집니다 — Word가 표째 지우는 것과 같은 의미론. 지워질 표 안에서 참조된 각주들만 미리 걷어 함께 삭제하면 끝. 거부로 남겨 뒀던 경계 사례가, 자료 구조를 한 층 내려가 보니 오히려 더 단순한 경로였다는 결말입니다.

덧붙임 3: 열 단계를 얹고 다시 재 보기 — 재실측의 두 가지 답

기능을 잔뜩(IME, 6개 스토리 편집, 노트, 선택 편집) 얹은 뒤 S3의 성능 벤치를 다시 돌렸습니다. 답은 두 가지였습니다. 첫째, 타이핑은 그대로(네이티브 min 23ms — 기준선과 동일). 새 기능들이 핫패스와 직교하게 설계됐다는 사실은 주장이 아니라 이렇게 재실측으로만 확인할 수 있습니다. 둘째, 다음 병목이 새로 보였습니다: Enter처럼 문단 수가 바뀌는 연산 후 브라우저에서 "34/63 페이지 다시 그림"이 찍힙니다.

여기서 진단 하나를 틀렸다가 정정했습니다 — 그 과정 자체가 교훈이라 남깁니다. 처음엔 "소스 id가 밀려서 내용이 같은 페이지도 다시 그려진다"고 썼습니다. 그럴듯했죠. 그런데 코드를 다시 보니 델타 해시는 id를 아예 안 섞고 있었고, 프로브를 돌리니 타이핑은 정확히 1/63페이지만 다시 그렸습니다. 34페이지 재렌더의 진짜 이유는 단순합니다: 문단을 끼우면 그 뒤 모든 페이지의 내용이 실제로 한 줄씩 밀립니다. 정당한 리플로우예요. Word도 같은 리플로우를 합니다 — 다만 화면에 안 보이는 페이지는 그리지 않을 뿐. 그래서 다음 최적화는 해시나 직렬화가 아니라 "지금 전부 그릴 필요가 있나"가 됩니다. 그럴듯한 진단은 코드와 프로브 앞에서만 진단입니다 — 재실측이 두 번 일한 날입니다.

그 답이 지연 렌더입니다: wasm은 "어느 페이지가 바뀌었나"(인덱스) 만 알려주고, SVG는 페이지별로 꺼내 씁니다. 뷰포트 근처만 즉시, 나머지 30여 장은 idle 시간에 8ms씩 잘라서. 핵심 불변식은 "꺼내는 SVG는 항상 현재 문서를 그린다"는 것 — 그래서 편집이 연달아 와도 미룬 페이지를 무효화할 필요가 없고, 드레인이 언제 돌든 결과는 옳습니다. Enter의 체감 비용이 335→211ms로, 즉시 그리는 페이지는 34장→2장으로 떨어졌습니다. Word가 늘 하던 일을 우리도 하게 된 겁니다.
