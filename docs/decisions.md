# 의사결정 기록

## D1. 밑바닥 개발 대신 rdocx 위에 쌓는다 (2026-08-21)

HWP와 달리 DOCX는 파서+레이아웃+렌더링을 갖춘 활성 오픈소스(rdocx, 27개
크레이트 162K LOC, MIT/Apache-2.0)가 존재한다. 같은 것을 다시 만들면 2년
뒤에 현재의 rdocx에 도달할 뿐이다. 에디터 계층에 집중한다.
리스크: 사실상 1인+AI 유지보수 체제, 0.x 파괴적 변경 → 포크 권리로 헤지.

## D2. 렌더링은 SVG, 글리프는 벡터 패스 내장 (2026-08-21)

canvas 대신 SVG를 선택: DOM 통합(히트테스팅에 `data-hit` 활용), 자기완결
문서로 배포 가능, 해상도 독립. 글리프를 `<defs>`+`<use>`로 중복 제거해
내장하면 뷰어 폰트와 무관하게 동일 렌더링 (1페이지 gzip ~40KB).
좌표 정밀도 교훈: scale 값은 소수 7자리 필요 (2자리 반올림 시 28% 오차).

## D3. 업스트림에는 최소 패치 + 공개 제안, 의존은 rev 고정 포크 (2026-08-21)

필요 API(`layout()`, `layout_with_fonts()`)를 22줄 패치로 유지하고 #37로
업스트림 제안. 수용 전까지 emptinessform/rdocx@svg-poc를 rev 고정으로 의존.
패치를 최소로 유지해 리베이스 비용을 억제한다.

## D4. 문서 위치 역매핑은 당분간 텍스트 매칭 우회 (2026-08-21)

레이아웃 출력에 소스 위치(provenance)가 없어 순차 텍스트 매칭으로 역산
(데모 문서 156/174 = 89% 매핑). 표 셀·마커는 편집 불가로 명시 처리.
근본 해결(레이아웃에 소스 위치 탑재)은 S3 전에 업스트림 제안 예정 —
동일 문구 반복 문서에서 매칭이 깨질 수 있어 제품 품질로는 부족하다.

## D5. 진행 방식은 rhwp 방법론 (2026-08-21)

AI 페어 프로그래밍 + 사람이 매 단계 확인하는 검증 우선 진행. 모든 단계는
실측 증거와 함께 worklog에 기록하고, 사용자 확인 게이트를 통과해야 다음
단계로 간다. 규칙은 CLAUDE.md.
