# 2026-08-22 — S11-1: 성능 재실측 (S3 기준선 갱신)

## 목표·범위

S3 성능 게이트(63페이지, 키 입력당 <30ms) 이후 S4~S10에서 얹은 기능
(IME, 6스토리 편집, Enter/병합, 노트 삽입·삭제, 빈 문단 세그먼트, 미주
타입 필드, 선택 편집)이 성능을 움직였는지 실측. bench.rs에 구조 연산
구간을 추가하고 브라우저 측정을 재실행. 최적화는 범위 밖(발견만 기록).

## 측정 환경

- 동일 700문단+표 14개 문서 (63페이지, out/bench.docx), 포크 7c114e8.
- 네이티브: `cargo run --release --bin bench` (+`RDOCX_BENCH_HF=1` 변형).
- 브라우저: 헤드리스, `state().lastMs`(wasm 호출 시간 = 증분 레이아웃 +
  델타 SVG + hits 직렬화), 2회 실행. 머신 노이즈 이력 있음 → min 중시.

## 결과 — 타이핑 (S3 대비 회귀 없음)

| 측정 | S3 기준선 | 현재 |
|---|---|---|
| 네이티브 키 입력 (HF off) | 24~30ms | mean 26 / min 23ms |
| 네이티브 키 입력 (HF+PAGE) | ~동일 | mean 24 / min 22ms |
| 브라우저 키 입력 | 64~103ms (부하 시 ~160) | min 69~71 / mean 100~121ms |

S4~S10 기능이 타이핑 핫패스와 직교함을 확인 — 증분 캐시(지문, 문단
캐시, 재시작 페이지네이션)는 그대로 작동.

## 결과 — 구조 연산 (신규 기준선)

노드 테이블이 바뀌어 페이지네이션 풀패스 폴백을 타는 연산들. 위치 3곳
(200/400/600문단)에서 각 1회, ms:

| 연산 | 네이티브 HF off | HF+PAGE | 브라우저 |
|---|---|---|---|
| Enter (분할) | 35~39 | 45~48 | ~500 |
| Backspace 병합 | 33~35 | 44~46 | ~450 |
| 형제 2문단 선택 삭제 | 32~35 | 47~53 | — |
| 각주 삽입 | 36~38 | 45~70 | — |
| 각주 삭제 | 35~36 | 42~49 | — |
| undo (스냅샷 복원) | — | — | ~400 |

- 네이티브 풀패스 폴백은 타이핑 대비 +10~20ms — 인터랙티브 예산 안.
- 브라우저 구조 연산 ~0.5s의 내역: 풀패스 wasm 레이아웃 + **34/63페이지
  SVG 재생성**. (첫 기록의 오진 정정은 아래.)

## 정정 (S11-2 착수 시 확인)

첫 커밋(9698d5d)의 "발견" 두 건은 **오진**이었다. 코드 재확인 + 프로브
실측(타이핑 "1/63 pages redrawn", Enter "34/63")으로 정정:

1. ~~소스 id 연쇄 시프트가 불필요 재렌더 유발~~ → 델타 해시
   (`hash_elements`)는 위치·글리프·색만 입력으로 쓰며 소스 id를 아예
   포함하지 않는다. Enter 후 34페이지 재렌더는 분할점 이후 내용이
   실제로 한 줄씩 밀리는 **정당한 리플로우**다 (Word도 같은 리플로우를
   한다 — 다만 화면 밖 페이지를 그리지 않을 뿐).
2. ~~hits JSON 전량 재직렬화~~ → hits도 이미 페이지별 해시로 델타
   전송(`hit_hashes`). 구조 연산에서 전 페이지 hits가 가는 것은 경로
   문자열이 실제로 전부 바뀌기 때문(정당).

남는 진짜 최적화는 "바뀐 34페이지를 지금 전부 그릴 필요가 있나"다 —
사용자가 보는 것은 1~2페이지뿐. → S11-2: 지연 SVG 생성.

3. cold layout 편차(1641 vs 578ms)는 디스크 캐시 워밍 차이로 판단.

## 결론

타이핑 핫패스는 기준선 유지(게이트 <30ms 계속 충족). 구조 연산은
네이티브에서 충분히 빠르나 브라우저에서 다수 페이지의 정당한 리플로우
렌더가 지배 — S11-2에서 가시 페이지 우선 지연 렌더로 대응.

# S11-2: 지연 페이지 렌더 (가시 페이지 우선)

## 목표·범위

구조 연산 후 리플로우된 30여 페이지 중 사용자가 보는 것은 1~2페이지
뿐이라는 S11-1 정정 결론의 실행: 변경 페이지 SVG를 즉시 전부 만들지
않고, 가시 영역만 동기 적용 + 나머지는 idle 드레인.

## 구현

- lib.rs: `RenderDelta.pages`(SVG 문자열 동봉) → `changed_pages`(인덱스만).
  `render_page_svg(layout, index)` 신설 — 페이지 1장 온디맨드 생성
  (히트 id가 페이지 로컬이라 독립 렌더러로도 번호 일치).
- wasm: `RenderOut.changed` + `page_svg(index)` (레이아웃은 캐시 —
  페이지당 SVG 생성 비용만).
- index.html `apply()`: 변경 페이지 중 뷰포트 ±1 화면 안(또는 DOM에
  아직 없는 새 페이지)만 즉시 `page_svg` 적용, 나머지는 `dirtyPages`
  집합 → requestIdleCallback 드레인(8ms 슬라이스). `page_svg`는 항상
  현재 문서를 렌더하므로 여러 편집에 걸쳐 미룬 페이지도 드레인 시점에
  자동으로 최신. 스크롤 시 근처 dirty 페이지 즉시 드레인(스테일 노출
  방지). `__t.dirtyCount` 훅.

## 검증 (실측, 63페이지 bench.docx, 페이지 30에서 조작)

| 연산 (wasm 호출 시간) | S11-1 (전량 렌더) | S11-2 (지연) |
|---|---|---|
| Enter | 335~529ms | **211ms** ("2/63 redrawn, 32 deferred") |
| Backspace 병합 | 374~479ms | **176ms** |
| 타이핑 | mean ~100 / min ~70ms | mean 104 / min 73ms (불변) |

- idle 드레인: Enter 후 dirty 32 → 수 초 내 0, 스크롤 없이도 소진.
  원거리 페이지(60) DOM의 data-hit 수 = 신규 히트맵 수(591=591) 일치.
- 회귀 13종 전부 그린 (cellsel/notesel/en/enops/noteops/note/shift/
  ux3/ux4/ime/split/roundtrip/empty) — apply() 전면 교체에 대한 검증.

남은 wasm ~200ms의 내역은 풀패스 레이아웃 + 63페이지 히트 수집/직렬화.
더 줄이려면 레이아웃 자체(업스트림 협력 영역) 또는 히트 지연화가 다음
후보지만, 체감 지연(캐럿 응답)은 이미 타이핑 2~3배 수준으로 안착.
