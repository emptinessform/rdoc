# 2026-08-23 — S26: 오픈 폰트 세트 (rhwp 방식)

## 목표·범위

사용자 지시: rhwp처럼 오픈 폰트를 최대 활용하고, 모바일 등 로컬 폰트가
없는 환경을 감안한 웹폰트 구성. 결과 SVG는 글리프가 벡터로 내장되므로
**뷰어 쪽은 원래 폰트 불필요** — 폰트가 필요한 곳은 wasm 레이아웃
시점이고, 우리 "웹폰트"는 HTTP로 받은 폰트 바이트를 `add_font`로
주입하는 것.

범위: OFL 폰트 2종을 한국 상용 패밀리명에 매핑하는 로더(main.ts),
포크의 caller 폰트 별칭 수정, Pages 워크플로 폰트 추가, 검증 픽스처 +
신규 스위트.

## 구성

- **폰트 (SIL OFL 1.1, CI에서 다운로드 — 저장소 미커밋)**:
  - Pretendard-Regular.otf (1.5MB) — 산세리프: Pretendard, 맑은 고딕
    (별칭), 굴림/굴림체, 돋움/돋움체, 새굴림, 나눔고딕, 함초롬돋움,
    Apple SD Gothic Neo, Noto Sans KR/CJK KR, 본고딕.
  - NanumMyeongjo-Regular.ttf (3.0MB) — 세리프: 나눔명조, 바탕/바탕체,
    명조/신명조/HY신명조/휴먼명조, 함초롬바탕, 은바탕, Noto Serif
    KR/CJK KR, 본명조, **궁서/궁서체(근사 — 오픈 필기체 부재)**.
  - Noto Serif CJK KR(~24MB)은 크기 때문에 배제, 나눔명조 채택.
- **로더**: 소스는 병렬 fetch, 등록은 선언 순서 — 먼저 선언된 소스가
  경합 패밀리명을 가짐. 로컬 `malgun.ttf`(개발 머신)가 "Malgun
  Gothic"/"맑은 고딕"을 선점하고, 없으면(데모/모바일) Pretendard가
  받음. 미등록 이름은 rdocx 번들 폴백.
- **포크 수정 1 (730f372, 업스트림 보고 후보)**: `FontFile.family`가
  지금까지 **무시**되고 있었음 — fontdb는 파일 내부 패밀리명으로만
  등록해, "바탕"에 나눔명조를 등록해도 커버리지 폴백으로만 동작.
  FontManager에 caller 별칭 테이블(요청명 소문자 → 실제 패밀리)을
  추가하고 resolve_font에서 정확 일치 바로 다음 순위로 시도.
  단위 테스트: Caladea 바이트를 "바탕"으로 등록 → "바탕" 해석이
  Caladea (수정 전엔 제네릭 산세리프로 표류).
- **성능 사고와 포크 수정 2 (7d821d8)**: 별칭마다 FontFile을 반복하면
  폰트 바이트가 별칭 수만큼 복제 — 별칭 ~40개에서 **매 레이아웃
  ~100MB 복사**가 발생해 데모 렌더 48→662ms, 키 입력 ~70→195~276ms
  회귀, 전체 배터리에서 타이밍 민감 스위트 3종(color/thumbs/ux3)
  실패로 표면화. 별칭을 바이트 없는 1급 개념으로 승격:
  `FontManager::set_caller_aliases((요청명, 대상 패밀리) 쌍, 무변경
  no-op/변경 시 해석 캐시 무효화)` → `Engine::set_caller_font_aliases`
  → `Document::layout_with_fonts_aliases_and_bundled_fallback`. wasm은
  `add_font_alias(요청명, 패밀리)` 노출, 로더는 폰트 3파일을 1회씩만
  등록하고 이름은 전부 별칭으로.

## 검증 (실측)

- 진단 분리: 픽스처(fontmap-test.docx — 동일 텍스트 4문단, 맑은
  고딕/굴림/바탕/궁서 요구)를 네이티브(시스템 폰트)로 렌더 → 글리프
  def 60종이 문단 간 비공유 = rFonts 처리 정상, 문제는 wasm 폰트
  등록 경로로 확정.
  - 참고: 한글 음절은 두 폰트 모두 전각(1em)이라 어드밴스 판별이
    안 됨 — 판별은 라틴 구간 총폭으로 (첫 시도의 교훈).
- 포크: oxml-layout 74/74, rdocx-layout 147/147 그린.
- fonts-test 스위트: **PASS** — 굴림 문단(→Pretendard)과 바탕 문단
  (→나눔명조)의 총폭이 상이, 바탕=궁서 총폭 동일(같은 세리프),
  24/24런 매핑. 수정 전에는 4문단 폭이 전부 동일(132.06pt =
  전부 커버리지 폴백)이었음.
- 네이티브 코퍼스: 14/14 그린 + lib 테스트 9/9 (최종 rev 7d821d8).
- 성능 재실측 (별칭 방식, 데모 문서): 렌더 39.4ms, 키 입력
  24.6/19.7ms — 중복 바이트 방식(662ms/195~276ms) 대비 정상화,
  S24 단일 폰트 시절(48.6ms)보다도 빠름.
- 배터리에서 드러난 2건 (폰트 변화가 노출한 기존 취약점):
  1. **applyFontColor 잠복 버그 (제품 수정)**: "색은 리플로우가 없어
     선택 refs 유효" 가정이 틀림 — 색 적용이 런을 분할하면 히트
     세그먼트가 재편성되어 {page,idx,k} refs가 낡음 (재현: 선택
     " 달려 " 4자 → 색 적용 후 같은 refs가 " 달" 2자). 문서 오프셋
     기반 재유도(refForOffset)로 교체. malgun 세그먼트 경계에서는
     우연히 일치해 이제껏 통과했던 것.
  2. **ux3 스위트 좌표 가정 (테스트 수정)**: shift+클릭 x=260
     하드코딩이 malgun 폭 전제 — 오픈 폰트에서는 줄이 짧아져 각주
     마커(장식 런)에 떨어짐. 대상 문단의 마지막 세그먼트 중심을
     히트 기하에서 유도하도록 수정 (S18 hf-test와 같은 패턴).
- 전체 배터리: **33/33 그린** (fonts-test 포함). 단, 이번 세션 말미에
  브라우저 데몬 부하로 "pending"(결과 미기록) 플레이크가 회차마다
  다른 스위트에서 7건 발생 — 전부 즉시 재시도에서 PASS, 동일 빌드
  기준 모든 스위트가 최소 1회 그린. 백그라운드 실행 2회는 외부
  중단되어 전경 분할 실행으로 완주.
- 시각 증거: docs/evidence/s26-fontmap.png — 맑은 고딕(malgun)·굴림

  M1 후보로 미룸.
