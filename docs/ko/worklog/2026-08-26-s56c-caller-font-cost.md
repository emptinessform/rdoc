# 2026-08-26 — S56c: 브라우저 회귀의 원인 = 캐러 폰트 경로 (wasm 한정)

## 목표·범위

S56b에서 다시 열린 "브라우저만 느린" 회귀의 원인 특정. 진단·계측만,
프로덕션 무변경.

## 도구

- `crates/rdoc-core/src/bin/bench3.rs`(신규) — **브라우저 경로를 네이티브로
  재현**. `doc.layout()` 대신 웹 앱과 같은
  `layout_with_fonts_aliases_and_bundled_fallback`을 실제 오픈 폰트 5종
  (malgun 포함 22 MB) + 별칭 40개로 호출. 700문단 → **58페이지로 브라우저와
  일치**. env: `RDOC_BENCH3_FONTS=0`, `RDOC_BENCH3_ALIASES=0`,
  `RDOC_BENCH3_PARAS=N`.
- 브라우저 A/B는 **빌드 산출물 2벌 보관 후 한 세션 내 교대** 방식으로 전환
  (`web/pkg-08` / `web/pkg-010`을 `web/pkg`로 복사 + `browse restart`).
  빌드 직후 수치가 부풀려지는 문제와 연속 측정 편향을 동시에 제거한다.

## ① 브라우저 회귀는 실재한다 (측정 방식 교정 후)

교대 측정, 3·4패스는 순서 반전 (bench.docx, 58p, 타이핑 mean ms):

| 패스 | 0.8 | v0.10.1 |
|---|---|---|
| 1 | 73 | 111 |
| 2 | 75 | 89 |
| 3 | 66 | 111 |
| 4 | 70 | 109 |

중앙값 71.5 → 110 = **1.54×**, 구간 겹침 없음. undo 1.24×, 셀 병합 1.40×.
(참고: 같은 빌드 안에서도 연속 3회가 64→89→155 ms로 흔들린다. 교대
측정이 필수인 환경이다.)

## ② 네이티브 동일 경로에는 회귀가 없다

bench3, 58페이지, 같은 폰트 5종 + 별칭 40개, 안정화 후 4회 (mean ms):

| | 0.8 | v0.10.1 |
|---|---|---|
| 캐러 폰트 5 + 별칭 40 | 69 / 52 / 62 / 63 (중앙 62.5) | 53 / 54 / 60 / 58 (중앙 56) |
| 캐러 폰트 없음 | 42 / 39 / 35 / 48 / 38 (중앙 39) | 26 / 27 / 26 / 28 / 30 (중앙 27) |

**네이티브에서는 v0.10.1이 같거나 더 빠르다.** → 회귀는 레이아웃 알고리즘이
아니라 **wasm 빌드에 한정**된다.

## ③ 원인은 캐러 폰트 바이트 (별칭 아님)

브라우저, **1페이지 문서**(demo.docx)로 구성만 바꿔 교대 측정
(타이핑 mean ms / undo ms):

| 구성 | 0.8 | v0.10.1 |
|---|---|---|
| 캐러 폰트 없음 (파일을 치워 fetch 실패) | 5·6 / 4·6 | 7·6 / 8·6 |
| 폰트 5종 + 별칭 40 | 26·32 / 22·25 | 44·67 / 62·77 |
| 폰트 5종, **별칭 0** | 25·27 / 31·29 | 69·54 / 116·71 |

- 캐러 폰트가 없으면 **두 빌드가 동일**하다(5~7 ms).
- 별칭을 전부 빼도 회귀는 그대로 → **F-X051 별칭 해석이 원인이 아니다**.
- 1페이지 문서인데도 폰트 등록만으로 0.8은 +20 ms, v0.10.1은 +50 ms가
  붙는다. 문서 크기와 무관한 **레이아웃당 고정 비용**이며 등록된 폰트
  바이트(22 MB)에 비례하는 성격이다.

메모리 압력 가설은 기각된다 — 1페이지에서 비율이 오히려 더 크다.

## 결론

브라우저 회귀 = `layout_with_fonts_*` 계열이 **매 재레이아웃마다 캐러 폰트
바이트에 비례하는 작업**을 하고, 그 비용이 v0.10.1에서 약 2.5× 커졌으며,
네이티브에서는 묻히지만 wasm에서는 지배적이 된다. 0.8도 같은 성질의 비용을
내고 있다(1페이지 +20 ms) — 즉 이 경로는 원래부터 개선 여지가 있고
v0.10.1이 악화시켰다.

우리 포크의 b19e06e(2026-08-23)가 같은 계열의 문제를 잡은 적이 있다
(별칭마다 폰트 바이트를 복제 → 매 레이아웃 ~100MB 복사, 70→200 ms).
그때는 별칭 중복이 원인이었고, 이번은 별칭이 없어도 발생한다.

## ④ 원인 지점 특정 — `matches_input`의 폰트 바이트 비교

`build_layout_input_with_fonts`는 **양쪽 핀 모두** `data.to_vec()`으로 폰트
바이트를 LayoutInput에 복사한다(22 MB/레이아웃). `load_additional_fonts`의
`self.additional_fonts == font_files` 바이트 비교도 **양쪽에 다 있다**.

v0.10.1에만 있는 것은 F-X052가 추가한 retained work context다
(`ReusableEngineContext`, engine.rs:497~578). 이 구조체는 `fonts`와
`images`를 통째로 들고 있고, `matches_input`이 매 레이아웃마다

```rust
&& self.fonts == input.fonts     // 캐러 폰트 22 MB 바이트 비교
```

를 수행한다. 즉 v0.10.1은 재레이아웃당 폰트 바이트를 **한 번 더** 훑는다.

**검증**: 포크 `exp/font-compare`에서 이 한 줄을 family + data.len() 비교로
바꿔 wasm 3종을 만들어 교대 측정.

1페이지 문서 (타이핑 / undo ms, 2패스):

| 빌드 | 타이핑 | undo |
|---|---|---|
| 0.8 | 30 · 26 | 23 · 29 |
| v0.10.1 | 39 · 48 | 54 · 56 |
| v0.10.1 + 얕은 비교 | **28 · 30** | **26 · 35** |

58페이지 실문서:

| 빌드 | 타이핑 | undo | 로드 |
|---|---|---|---|
| 0.8 | 103 · 86 | 158 · 162 | 6443 · 5503 |
| v0.10.1 | 119 · 107 | 171 · 211 | 5812 · 6585 |
| v0.10.1 + 얕은 비교 | **93 · 82** | **138 · 156** | 5279 · 4722 |

**한 줄 변경으로 회귀가 사라진다.**

`load_additional_fonts`까지 얕게 바꾼 2단 패치(`exp/font-compare2`)는
타이핑에 추가 이득이 없었으나(노이즈 범위) **문서 로드가 일관되게 빨랐다**
(4135 · 4474 ms vs 0.8의 5932 · 5366) — 이쪽은 0.8에도 있는 비용이므로
**우리 포크에도 적용 여지**가 있다.

> 실험 패치는 얕은 비교라 일반적으로는 **부당하다**(길이가 같은 다른 폰트를
> 구분 못 함). 올바른 수정은 지문/해시를 곁들이거나 `FontFile.data`를
> `Arc`로 만들어 O(1) 동일성 비교를 하는 것이다.

## 업스트림 게시 (2026-08-26, 사용자 승인)

**새 이슈 #54** — https://github.com/tensorbee/rdocx/issues/54
(#53과 별건). 격리 표(폰트 없음/폰트+별칭/폰트만), 네이티브에는 회귀가
없다는 점, 원인 한 줄(`matches_input`의 `self.fonts == input.fonts`),
얕은 비교 패치로 회귀가 사라지는 3빌드 교대 측정표, 수정 제안(지문 또는
`FontFile.data`를 `Arc`로), 그리고 `images`도 같은 구조라는 지적과
`load_additional_fonts`는 양쪽 핀 공통이라는 점을 포함. 측정 편차(같은
빌드 2.4×)와 실험 패치가 부당하다는 단서도 명시.
- 우리 포크 적용 검토: `load_additional_fonts`의 바이트 비교를 지문 기반으로
  바꾸면 0.8 핀에서도 문서 로드가 빨라질 수 있다(위 측정). 별도 단계.
