1. What this project does

We are building a lightweight editor that reads a .docx file, draws it in the browser like a real sheet of paper, and lets you type on it directly. The heavy computation — placing glyphs, breaking pages — is done by Rust compiled to wasm, and the drawing is SVG (vector graphics). The layout engine is the open-source rdocx, and the improvements we need are proposed back to upstream.

2. What happens when you press one key — the layout pipeline

Every time a word processor inserts a single character it has to work out again: "how many lines is this paragraph now? If it grew a line, does the rest push onto the next page?" That whole computation is called a relayout. Its stages are these.

Block
One paragraph, fully line-broken to the page width. A finished piece that says "this paragraph is these three lines". A table is one block too.
Shaping
Asking the font file to turn a string into actual glyph shapes and per-glyph widths. Scripts where letters join up — Korean, Arabic — make this more expensive than it sounds.
Pagination
Filling finished blocks onto a page from the top and moving to the next page when one overflows. This is where "how many pages is this" is decided.

3. Why it was slow, and how caches saved it

The first measurement on a 63-page document was 1,144ms per keystroke. Over a second, which makes typing impossible. Nearly all of it turned out to be the cost of doing the same work from scratch every time.

CulpritWhat it didCost
System font scanre-read every font installed on the machine, every time~750ms
Font file copiesre-read and copied a 13-20MB Korean font file every time~230ms
Rebuilding blocksre-broke all 700 paragraphs, including untouched ones~100ms
Paginationredistributed all 63 pages~19ms

Every fix is the same idea — store what you computed once, and hand back the stored copy when the same work comes around again. The font scan became once per process; font files are read once per path; shaping results are stored under a (font, string, size) key; blocks are reused whenever the paragraph's content has not changed. Those four caches took it from 1,144ms to 101ms, and the work in sections 4 and 5 took it to 37ms.

The lesson — an editor is not a converter. Costs that are invisible when you convert a file once become cost per keystroke when they repeat on every key. So performance work on an editor is mostly finding the repeated work and caching it.

4. Fingerprints — telling "nothing changed" quickly

Comparing a whole paragraph character by character to answer "is this the same as last time?" is itself slow. Instead the paragraph's content is summarized into one large number. That summary is called a hash, or a fingerprint. Same content, same fingerprint; different content, (effectively certainly) a different fingerprint. One number comparison settles same or different.

At first we printed the whole paragraph structure to a debug string (format!("{:?}")) and hashed that — and building the string alone cost ~20ms per keystroke. So we wrote a dedicated worker: body text is hashed as raw bytes, and only small structures like formatting go through a debug string. It summarizes the same thing for a fraction of the cost.

The trap in caching — if something is missing from the cache key (the fingerprint), the cache says "unchanged" for something that did change and hands back a stale result. Example: the "3." in a numbered list depends not on the paragraph itself but on how many paragraphs came before it, which a content-only fingerprint misses. So numbered paragraphs are excluded from the block cache. Half of cache design is deciding what goes in the key.

5. Keeping the cache alive across undo — carrying the engine over

Undo restores a whole previous document state, which means constructing a new document object. The caches (the shaping memo, the block cache) hung off the engine inside the old object, so building a new one threw the entire cache away. The first relayout after an undo was about twice as slow as typing.

The fix is like taking your furniture with you when you move: before swapping the document object, pull the engine (caches included) out of the old one and put it into the new one. Two APIs do that (take_layout_engine / set_layout_engine). The caches are keyed by content, so they are safe no matter which document object they hang off. Result: undo and redo run at typing speed (75-91ms in wasm).

6. Restartable pagination (done — 37ms to 24-30ms per keystroke)

One large remaining chunk of the per-keystroke cost was pagination (12-15ms). Change a single character and all 63 pages get redistributed. But think about it: edit a paragraph on page 5 and pages 1-4 cannot possibly change, and if the line count holds, neither can page 6 onward.

It takes three ingredients.

  1. The list of block fingerprints — comparing this keystroke's fingerprints against the previous ones side by side gives you the first block that differs (the divergence point).
  2. Checkpoints — during pagination we record the points where "this block started a fresh page cleanly". Cleanly means the paragraph was not split across the page boundary and no footnote was carried over. At such a point the paginator's state is effectively empty, so restarting from it later produces the same result.
  3. Splicing — while redistributing after the divergence point, if we reach a point where the remaining blocks are identical to last time and the current page number matches last time's, we attach the previous tail pages wholesale and stop. Typing usually does not change the page count, so in practice only one or two pages get redistributed.
Why this needs care — pages are influenced by their surroundings. A keep-with-next property looks ahead at the first line height of the next block; a floating drawing can put an image from a later block onto an earlier page; footnotes can continue across a page. So documents with those features (floating drawings, multiple sections, and so on) safely fall back to full pagination, and checkpoints are only taken outside the range of such effects. And a test always enforces "cached path result == full recomputation result".

Result: pagination went from 12-15ms to 1-3ms. Of 63 pages only the four around the change are actually redistributed ("29 prefix + 4 rebuilt + 30 spliced"). Tables are cached under a fingerprint key like paragraphs, and the whole keystroke came to 24-30ms on average — meeting the 30ms gate we had set.

7. What finishing it taught us — checkpoint traps and the power of sharing

Trap 1: where to take the checkpoint

The first implementation said "at the top of the loop over blocks, if the page is clean, take a checkpoint". Running it produced not one checkpoint. The reason: page boundaries do not happen between loop iterations. "This paragraph does not fit in the remaining space → close the page → place the paragraph on a new page" happens inside the paragraph placement function, so by the time control returns to the top of the loop the new page already has content on it. The checkpoint had to be taken at the entry to the block placement function. Lesson: when you record state, check in the actual control flow when that state really exists. The loop in your head and the real control flow are different.

Trap 2: save the work, then spend it all on copying

Even after reuse worked, total time went up. The culprit was copying: for the cache to hold pages it needs a copy to hand to the caller, and deep copying 63 pages cost ~12ms — about what the pagination saved.

The fix is Rust's Arc, a reference-counted shared pointer: instead of copying a page, both sides hold a handle to the same original. Copying drops to 0ms, and only when someone actually has to modify a page (substituting a page-number field, say) is that one page copied at that moment — copy on write. Lesson: a cache only really pays once you count the cost of getting the data back out. And performance work has to be measured at every step — "it must be faster now" was wrong twice.

8. The secret of Korean input — IME composition and grouping undo

In English one key is one character, but Korean assembles several keys into one syllable: ㅎ + ㅏ + ㄴ = 한. The OS program that does the assembling is an IME. The browser reports the assembly through three events: compositionstart → compositionupdate (in progress — it keeps changing through "ㅎ", "하", "한") → compositionend (committed).

On every update the editor reflects the change on screen by deleting the previous composing character and inserting the new one (replace_range). A full relayout runs for each of those, but thanks to the performance work in sections 3-7 that is tens of milliseconds per key — fast enough to feel live. The performance work is what made the feature possible, in that order.

The core problem was the unit of undo. The editor pushes a document snapshot onto the undo stack before every edit, and the intermediate composition steps are edits too — so a single "한" pushed three snapshots. The fix: push one snapshot at composition start and set a flag that suppresses pushes during composition (begin_composition / end_composition). If the composition is cancelled (it ends with an empty string), the document is identical to the snapshot, so that snapshot is dropped as well — otherwise Ctrl+Z would have one press where nothing appears to happen.

What we learned — what the user sees (screen updates) and what history records (undo units) are separate axes. "Show it finely, record it coarsely" is basic editor grammar: the same principle later applies to dragging, autocorrect and paste normalization. Verification follows the same split: intermediate states are checked by reading the screen text between events, and undo is checked by counting presses (7 automated scenarios, all passing).

Addendum: the preedit underline belongs on the glass, not in the document

Drawing the underline under composing text by adding and removing an underline format in the document would make undo consistency hard all over again. Instead we used the same mechanism as the caret and the selection highlight: draw the underline only on a transparent "pane of glass" laid over the document (an SVG overlay). The document never knows the underline exists, so there is nothing to remove whether the composition commits or is cancelled. Splitting the UI into "transient marks on the overlay, permanent content in the document" makes state management dramatically simpler.

9. A serial number hidden in the fingerprint — the cache that dies quietly

Adding a page-number footer ("Page N") to the benchmark made the caches miss across the board. The diagnostic log said "the environment changed" on every keystroke, but nothing in the document had changed. Splitting the hash per component showed that only the footer hash differed each time.

The culprit: source_id, a debugging aid on the field struct that takes a new number from a global counter on every parse. Our fingerprint hashed the struct's whole debug output, so a serial number unrelated to content changed the print every time. Silent failures like this are the dangerous kind: the result stays correct, it is merely slow. The fix: hash only what layout actually reads from a field (the instruction string, the stored display value, the dirty flag) instead of its debug output.

Two lessons. (1) Using a debug string as a cache key for convenience is signing something without knowing what is inside it. Put only meaningful fields in the key, explicitly. (2) Caches die quietly — correctness tests do not catch it. Plant a diagnostic that shows whether the cache hit (ours is RDOCX_TIMING) from the start and the problem shows up immediately as a number ("env changed" ten times).

10. Glyphs know where they came from — source maps and table cell editing

Working out "which paragraph, which character offset" a glyph on screen corresponds to is called reverse mapping. Until recently the layout output carried no origin information, so we searched the document text for the on-screen string and guessed the position (text matching). Two occurrences of the same wording could be confused, and table cells were given up on entirely.

Provenance — the origin tracking we proposed upstream — shipped officially in v0.8.0, so every fragment of the layout output now carries a certificate saying "I am this character range of this paragraph in the document". We turn that certificate into a path string ("d/8.1.0.0" = body item 8, a table, row 1, column 0, first paragraph), attach it to each glyph on screen, and on a click edit the document directly through that path. Once guessing became certainty, table cell editing simply opened up — typing, Korean composition, replacing a selection, undo, all identical to the body.

What we learned — when designing addresses, separate "the nth thing on screen right now" (a result-local id) from "where this is in the document structure" (a path). Ids change with every layout, but paths are stable across an edit, so the caret and selection state on the JS side is held purely as paths. And when infrastructure (the source map) is proposed upstream and becomes official, the feature on top of it (cell editing) is finished simply by removing the workaround — a workaround is debt, and contributing the infrastructure is repaying it.

Addendum: headers live in a different drawer

The same path scheme opened header and footer editing. One difference: body paragraphs live in the in-memory document tree, but a header is serialized into a separate XML part inside the .docx — a different drawer. So editing becomes three steps, "take it out (parse) → change it → put it back (reserialize)", and the part's relationship list is preserved so that other things in the drawer (image references, for example) are left alone. The story prefix of the path (d/ h/ f/) already says which drawer it is, so the editing operations themselves are literally the same code in all three places. Characters that are computed, like a footer's page number, have no certificate of origin (by design), so clicking them places no caret — being uneditable is itself the safety mechanism.

Addendum 2: footnotes are a typed field, endnotes are a drawer — and the source of truth

Footnote and endnote editing opened the last of the six stories. An amusing asymmetry: within the same library, footnotes lived as a typed structure in memory (modified in place, nothing to take out), while endnotes lived in a drawer (an XML part) like headers. Thanks to path dispatch our editing code does not have to know the difference.

That did expose an existing defect. When laying out footnotes the engine read only the drawer, so a footnote just added in memory and not yet saved did not appear on screen. When the same data lives in two places you have to decide which one is the source of truth and make every read go there — if the structure is "lift the drawer into memory on open, edit in memory", then reads must look at memory too. This inconsistency never showed in a document converter (which always reads the saved copy) and surfaced the moment a live editor was put on top. A new consumer is the best tool for testing old code's hidden assumptions.

Addendum 3: promoting endnotes — a refactor that removes the asymmetry

We eventually removed the asymmetry from addendum 2. Endnotes became the same kind of typed field as footnotes. It is called a promotion because the status of the data changes: an XML blob that used to be parsed out of a drawer and reserialized back on every edit becomes a struct parsed once at open time and resident in memory. 

Before promotion (drawer)            After promotion (typed field)
─────────────────────────            ─────────────────────────────
per edit:                            once at open:
  read the part XML                    part XML → struct
  → parse → modify                   per edit:
  → serialize → write back             modify the struct in place
                                         (just mark it dirty)
on save:                             on save:
  already in the part                  if dirty, struct → XML once

Three rules come with a promotion, and they are the point. (1) Lift on open: if the part exists, parse it into the field. (2) Reads look at the field: layout sees edits before they are saved (the footnote defect from addendum 2 never existed for endnotes). (3) Save only when dirty: if nothing was edited, the original part bytes are preserved untouched — the courtesy of not casually reserializing a document you did not write.

The payoff was immediate: Enter (split) and Backspace (merge) in endnotes came out as the same few-line functions as footnotes, and the two branches on the wasm side that used to refuse with "endnotes unsupported" became calls into a real implementation. Data of the same shape has to be handled by code of the same shape for special cases to disappear.

Insert and delete (Ctrl+Alt+E, Ctrl+Alt+D) followed by moving the footnote version over almost verbatim — after the promotion the only thing that distinguishes the two kinds of note in code is the tag name of the reference run (footnoteReference vs endnoteReference). On the shortcut side we unified in the opposite direction: delete is a single Ctrl+Alt+D, and which kind of note it removes is decided by the prefix of the path the caret sits on (fn/, en/). To the user this is one concept — "delete the thing I am in" — not two shortcuts by note type.

11. Deleting several paragraphs — siblings, scattering, and transactions

The moment a drag selection leaves a single paragraph, "delete" turns into a hard problem, because where the selection starts and ends produces two completely different shapes. 

Shape 1: siblings                     Shape 2: scatter
neighbouring paragraphs in one box    different boxes (cell → next cell)

  ┌─ cell ────────┐                    ┌─ cell A ┐ ┌─ cell B ┐
  │ para 1  Te[xt  │                    │ T[ext   │ │ Gl]yph  │
  │ para 2  ab]cd  │                    └─────────┘ └─────────┘
  └───────────────┘
  → like Word: cut head and tail,      → cell structure cannot merge!
    empty the middle, merge into one      strip text out of each paragraph

Shape 1 is the same algorithm whatever the box is: cut the tail of the first paragraph, cut the head of the last, empty the paragraphs in between, then merge them all into the first. Body, table cells, headers, footnotes and endnotes already shared one operation, "merge into the previous sibling" (section 10, addendum 3), so the new code came out as a single 40-line function that never asks which box it is in. Strip the last number off the path and you have the box key; equal keys mean siblings.

Shape 2 is one Word does not merge structurally either — delete a selection crossing cells and the text disappears while the table stays. We use the same approximation: walk the on-screen hit list (which paragraph and character offset each glyph is) to collect the covered range per paragraph, and hand wasm one list saying "delete [1..4) of this paragraph, [0..2) of that one". Different paragraphs do not shift each other's offsets, so ordering is not a concern.

The real lesson of this stage is the third one: an operation with several steps can fail at several steps. In the test that rejects a body selection crossing a table (a table in the middle makes merging impossible), the rejection worked — but the first paragraph's tail had already been cut. The editing core was structured to "drop the checkpoint on failure and leave the document alone", and for single-paragraph operations failure means nothing happened, so the defect had hidden for months. The fix is the transaction rule itself: on failure, roll back to the checkpoint. In an editor, "partial success" is another way of spelling data corruption.

Addendum: the screen is one sheet but the document has layers — and events only come when something moves

What caret ↑/↓ taught us: you must not look for "the line directly below" on screen. At the bottom of a page, footnote blocks and the footer are drawn after the body, but they are not the body's next line — they are lines of a different story. In Word, pressing ↓ on the last body line skips the footnotes and goes to the body of the next page. So line movement looks for "the nearest line in the same story", not the nearest line — a filter that is one path-prefix comparison (d/, fn/, en/…), and that restores to a coordinate search the logical structure of the document that coordinates do not carry.

What drag auto-scroll taught us: browser events arrive only when something changes. Hold the mouse button and park the pointer motionless at the edge of the screen and no more mousemove events come. So "keep scrolling while at the edge" cannot be built out of event handlers alone; you remember the last pointer position and let a requestAnimationFrame loop scroll and re-extend the selection every frame. Events are notifications of a state change and continuous behaviour belongs to a loop — an old dichotomy in UI code.

Addendum 2: the zero-width character — when a selection covers a marker

A footnote marker (²) is one character on screen, but in our text offset space it has zero width (a reference run has no text). So deleting a selection used to leave the marker behind as a ghost — a delete that only trims text has nothing to catch. Word deletes the whole note when its marker is inside the selection.

The fix is to ask separately, before deleting, "which markers does this range cover?". Define a marker's position as the number of text characters before it and the condition for a range [start, end) covering it is start < pos < end. Two interesting corners: (1) because the width is zero, a marker exactly on the boundary cannot in principle be told inside from outside (the caret before and after the marker share one offset), so we conservatively delete only when it is definitely interior; (2) note removal can be done before the text deletion — a reference run is zero width, so it shifts no character offsets at all. Freedom from ordering keeps the code simple.

The last piece of the puzzle was a body selection crossing a table. The sibling algorithm's "empty the middle paragraphs" fails when the middle is a table (that is where section 11's atomic rejection bites). But at the top level of the body the sibling index is the body content index, so removing the middle outright instead of emptying it makes paragraphs and tables disappear through the same code — the same semantics as Word deleting the table with the selection. Collect the footnotes referenced inside the doomed table and delete them along with it, and that is all. The edge case we had left as a rejection turned out, one layer down in the data structure, to be the simpler path.

12. Finishing the editor — a record of reuse

Almost everything after S11 — re-measurement and lazy rendering, find and replace, the clipboard, formatting, table structure, images — was built by reusing and combining operations that already existed. The notes below are the design lessons that kept recurring.

Measuring again after ten stages — two answers

After piling on features (IME, editing in all six stories, notes, selection editing) we re-ran the performance benchmark from section 3. It gave two answers. First, typing was unchanged (native min 23ms, identical to the baseline). That the new features were designed orthogonally to the hot path is not something you assert — re-measuring is the only way to confirm it. Second, the next bottleneck became visible: after an operation that changes the paragraph count, like Enter, the browser reported "34 of 63 pages redrawn".

Here we got a diagnosis wrong and corrected it — the process itself is the lesson, so it stays on the record. The first write-up said "source ids shift, so pages with identical content get redrawn". Plausible. But rereading the code showed the delta hash never mixed ids in at all, and a probe showed typing redrew exactly 1 of 63 pages. The real reason for 34 redrawn pages is simple: inserting a paragraph really does push the content of every following page down by a line. That is legitimate reflow. Word reflows the same way — it just does not draw the pages you cannot see. So the next optimization was not about hashing or serialization but about "do we need to draw all of this right now?". A plausible diagnosis is only a diagnosis in front of the code and a probe — a day where re-measuring did the work twice.

That answer is lazy rendering: wasm reports only which pages changed (indices), and SVG is pulled per page. Pages near the viewport render immediately; the other thirty or so are drained during idle time in 8ms slices. The key invariant is "an SVG pulled out always draws the current document" — so back-to-back edits never need deferred pages to be invalidated, and the drain is correct whenever it runs. Enter's felt cost went from 335ms to 211ms and the pages drawn immediately from 34 to 2. We finally do what Word always did.

Find is not new state, it is a combination of existing state

Building Ctrl+F, we tried hard not to invent any new state. "The current match" is not a separate concept — it is just the existing selection, so typing over a match replaces it (as in Word) and Ctrl+C copies it for free. Only the other matches get an orange overlay, and that is the same "pane of glass" pattern as the preedit underline (section 8's addendum) — nothing is left in the document. Matches going stale after an edit took one line: "if the panel is open after an edit, search again". Rather than caching search results and managing invalidation rules, making it cheap enough to recompute every time (45ms to search 63 pages) was much the simpler design.

The interesting part of replace (Ctrl+H) is "replace all = one undo". The whole match list goes over in a single wasm call, and it is applied from the back — replacing an earlier match in a paragraph shifts the offsets of later ones, but going backwards leaves the earlier offsets intact. And having made search non-overlapping like Word (the next scan starts at the end of the match) becomes the safety net here: replacing "aa" with "b" in "aaaa" never rescans the result ("bb") in this single pass, so a replacement containing the search term can never loop forever.

Paste is a replay of typing

We did not design multi-line paste as a new operation. Pasting "one\ntwo\nthree" has to be exactly the same thing as typing one, Enter, typing two, Enter, typing three. So the implementation is precisely that: insert a line, split, move to the next paragraph, repeat — merely wrapped in a single wasm call so it is one undo. Being a composition of existing operations (insert and split), it works for free in all six stories, including pasting inside a footnote. When a new feature is expressed as a replay of existing operations, its verification inherits the existing verification too.

Paragraph alignment (Ctrl+L/E/R) went the same way. Because text editing had been routed from the start through one gate — a paragraph handle shared by all six stories (with_paragraph_at) — alignment was a matter of putting one set_alignment line through that gate. Body, table cell, header, footnote or endnote alike; if the selection spans several paragraphs the path list goes over at once, so undo is one step too. Dig one good gate and the cost of a new verb stops depending on the number of nouns (stories).

Writes must be atomic — the zero-byte incident

A tooling story. A Python patch script editing a page died on an encoding error immediately after open(file, "w"). The problem is that "w" truncates the file the moment it opens it — if the write then fails, you are left with a zero-byte file containing neither the original nor the new content. index.html evaporated exactly that way, and was restored from the previous commit in a minute (the moment committing at every stage proved to be a safety net). Two lessons: (1) finish conversions that can fail (encoding!) before opening the file, and write only once the bytes are in hand; (2) better still, write to a temporary file and swap it in — an atomic write. Making a half-written state impossible is exactly the principle of section 11's edit transaction, applied to build tooling.

Do not touch what you do not understand — and the third guest

A principle learned adding and removing table rows and columns: pieces of a document our model cannot fully represent (raw XML blobs, content controls) are preserved with an index recording which row they sat before. Insert a row and all those indices are off by one — we could fix them up, but moving data we do not understand by guesswork is dangerous. So the answer is to refuse structural operations on such tables. "Change only what you understand completely, and preserve the rest byte for byte" — this document library's founding principle, the same grain as dirty-only saving in section 10's addendum 3 — repeats here.

Image insertion, meanwhile, was almost free to design, because it was the third guest of the pattern "split a run at a character offset and insert a zero-width special run" (footnote reference → endnote reference → image drawing run). A pattern used twice is a coincidence; used three times it is structure. At some point the design question for a new feature stops being "how do we build this" and becomes "which of our patterns is this the nth guest of?".

One real-world document taught its own lesson. A hospital billing receipt — six tables nested inside tables, 59 vertical merges, 44 rows saying "this row is exactly this tall" (hRule=exact), borders and spacing all hidden in the table style — exposed six holes in our layout at once (nested tables flattened, merged-row height blowup, exact ignored, table style not cascading, empty paragraphs falling back to 12pt, cell-anchored stamps lost). Months of synthetic demos would never have produced that combination. A real document tests the product of your features, not the list of them — and it teaches the order to fix them in: 4 pages → 3 → 2 → 1, each defect removed making the next one appear in measurable form.

The two finishing touches had the same grain. Tab navigation in tables (select the next cell; add a row at the last one) was not new code but a combination of the add-row operation and a paragraph selection helper, and text color was another guest of the same "split the run and set it" pattern as font size. Color does have one subtle but principled difference: it does not change glyph geometry, so there is no reflow and the selection can be kept as is (size reflows the lines, making the selection coordinates stale, so it collapses to a caret). Even riding the same pattern, the UX details are decided by the physics — by what actually moves.

13. From prototype to product — what M0-M2 taught us

After deciding "the prototype is good enough", the first work was to leave the code alone and make the structure fit a product (M0). Only then did features (M1) and document features (M2) get stacked on top. The order mattered: with the structure in place first, every feature after it landed as a small diff.

13.1 Names and places first — workspace, TypeScript, runner

All three M0 stages were work that made the code not one line smarter: (1) rdocx-svg-poc → crates/rdoc-core plus a root web/ workspace; (2) 1,580 lines of inline JS → ten web/src/*.ts modules (shared state promoted into a single S object, so every cross-module mutation is visible by its S. prefix); (3) an ad-hoc test loop → web/tests/run.sh. The verification criterion was the same for all three: if the battery is green with the suites unmodified, the move was pure.

13.2 Korean that looks right on machines with no fonts — open fonts and aliases

Because the output SVG embeds glyphs as vectors, the viewing side needs no fonts at all. Fonts are needed at exactly one point: wasm layout time. So the demo downloads two open fonts (Pretendard, NanumMyeongjo) and maps them as aliases onto ~40 commercial family names like 굴림, 돋움, 바탕 and 궁서. That work uncovered a latent bug — upstream's FontFile.family was in fact being ignored (reported as #44) — and measurement caught that the naive implementation, duplicating the font bytes for each alias, was copying ~100MB on every keystroke, which we redesigned into an alias API that carries no bytes. The lesson: if the same data has to be registered under different names, separate the names from the bytes.

13.3 "It saves but you cannot see it" — synthesized bold and italic

A user reported that B/I did nothing in the demo. The formatting was stored in the document and survived the round trip — the problem was that every loaded font was a Regular face, so turning on bold produced the same glyphs. We solved it the way Word does: load a real Bold face, and let the renderer synthesize the styles that do not exist (Korean italic has no face in the ecosystem at all) — bold as a same-color stroke, italic as a skewX. And we added visual assertions to the tests; a test that only checks document state and never looks at the screen will miss this class of bug forever.

13.4 Switching views is not editing

A distinction learned from track-changes view (S36): drawing the same document under a different projection (final ↔ show markup) must not enter history. Conversely, enforcing read-only has to be done at the single point every mutation passes through (edit()), not in each scattered piece of UI, so that features added later are protected automatically.

13.5 Two accidents caused by tooling — pipes and a shared clone

(1) cargo build | tail exits 0 even when the build fails (a pipeline's exit code is the last command's). That pushed a commit with a broken build and ran tests against stale wasm, twice in one day. The build chain now checks ${PIPESTATUS[0]}. (2) A fork clone can be shared with another project — git add -A swept up someone else's uncommitted WIP. Commits now name their files, and git status comes first. Both accidents were recovered immediately thanks to per-stage verification and an honest log.

13.6 Growing together with upstream

Many fork commits in this stretch became upstream candidates too: font aliasing (reported as #44), ensure_list_num for lists, cell merge/split, and view-option layout. Conversely, things upstream already had (line spacing, page setup, RevisionView) needed no fork changes at all. The habit of searching upstream before implementing made several stages free — and once we paid tuition by adding a duplicate of a getter that already existed, then reverting it.
